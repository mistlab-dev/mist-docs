# 产品架构视角：中小厂排产/交期该怎么落

> 前三份：`01-需求整理`（痛点证据）→ `02-整合稿`（市场格局与定价）→ `03-AI融合与发散`（未来路径）。
> 这一份换视角：**从产品架构师角度看，这东西到底该怎么建、建在哪、先建什么。**
> 方法：不只看外部调研，**先把我们两个仓库的真实代码能力摸清**，再判断。

---

## 一、最重要的发现：一个架构错配

### 1.1 文档模型 ≠ 业务数据模型

我先把 mist-docs 的存储链路读了一遍：

```
SheetEditor.vue  ──保存──▶  handler  ──▶  service.CreateDocument  ──▶  store.WriteVersion
                                                                        │
                                                                        ├─ crypto.EncryptDocument(data)
                                                                        └─ os.WriteFile(...)  ← 加密 blob 落盘
```

而 MySQL 里 `md_documents` 只有：`id / folder_id / department_id / title / type / file_path / file_size / version / locked_by / status / ...`

**结论很硬：表格内容不在数据库里，是一个加密文件。后端不解析它。**

我专门验证了这一点——`internal/handler/` 和 `internal/service/` 里**没有任何对 sheet 内容的 `json.Unmarshal`**。后端只当它是二进制。

**这带来一个直接后果**：

> 交期提醒需要回答「**哪些订单 3 天内到期？**」
> 但后端无法用 SQL 查询，因为它只能把每个 sheet 文件**解密 + 解析**才能知道里面写了什么。

一次性扫描所有 sheet、解密、解析、比较日期——小规模能跑，但这是**架构上的味道**：你为了一个"提醒"功能，把文档系统的加密边界和 blob 模型都捅穿了。

### 1.2 为什么会这样？因为文档和台账是两种东西

| | 文档（Document） | 台账（Ledger / 订单） |
|---|---|---|
| 典型操作 | 打开、编辑、协作、版本、导出 | 查询、过滤、聚合、排序、扫描、告警 |
| 数据形态 | 不固定，人创作 | 结构固定，有字段语义 |
| 存储选择 | **blob + Yjs 协同**（对的） | **DB 行 + 索引**（必须） |
| 规模 | 几十~几千个文件 | 几万~几十万行 |

**Excel 模板之所以失败，根因就在这里**——它让**一个文件既是数据、又是界面、又是唯一副本**。所以：
- 查不了（想统计只能自己拉透视表）
- 扫不了（没有服务端）
- 联不动（改一处全盘手动改）
- 提醒不了（文件不会自己说话）

**我们不能重复这个错误。**

### ✅ 架构结论一

> **交期看板要做成「实体 + 视图」，不是「一个表格文件」。**
>
> - **台账**（订单/工单）：DB 行，带 `due_date` 索引 → 可查、可扫、可告警、可聚合、可喂 AI
> - **表格**（自由分析）：保留现有 sheet，用于产能表、班次表、临时测算这类一次性的东西
>
> 两者是**互补**，不是替代。sheet 不改成台账，台账也不假装是 sheet。

**而这也修正了我上一份文档的说法**。我在 `02-整合稿` 里写"交付形态是一张表 + 一个提醒"——**那个表述是欠明确的**。准确的版本是：**交付形态是一块看板，底层是结构化台账，表格只是它的一种视图形态。**

## 二、第二个发现：服务端能力是错配的

我把两个服务的实际能力列出来，对比很刺眼：

| 能力 | mist-docs | mist-team-server |
|---|---|---|
| **定时调度器** | ❌ **完全没有**（无 cron / 无 ticker） | ✅ **4 个**：audit_purge、agent_offline、sop_generate、inspection |
| **AI 运行时** | ❌ 无 | ✅ `internal/ai/` 全套（ProposedAction / grants / trace / redact / sop_analyzer / tools） |
| **规则引擎** | ❌ 无 | ✅ `command_rules`（pattern / match_type / scope / action / priority） |
| **出站推送** | ⚠️ 有 webhook CRUD（`webhook.go`），无调度触发 | ✅ webhook + 巡检告警 |
| **表格 UI** | ✅ SheetEditor + 公式引擎 + 协同 | ❌ 无 |
| **文档权限/分享** | ✅ `permission.go` + `share.go` + 外链 | ⚠️ 团队级 |
| **通知表** | ✅ `md_notifications`（只有被动的"读取/已读"） | — |
| **WebSocket** | ✅ `ws/hub.go`（文档协同房间） | ✅ `agentbus`（对 Agent） |
| **MCP** | ❌ | ✅ `internal/mcp/`（可对外暴露能力） |
| **私有化** | ✅ 已是 | ✅ 已是 |
| **跨库访问** | — | ✅ **已经在做**：`md_doc_fragments` JOIN `md_documents`（同库 `mist_team`） |

**看出来了**：

- **mist-docs 是"人的界面"**：有编辑器、权限、分享、协同、通知表 —— 但**没有任何"主动做事的"能力**（无调度、无规则、无 AI）
- **mist-team-server 是"机器的大脑"**：有调度、AI、规则、MCP、Agent 通道 —— 但**没有业务界面**

这两个服务的定位其实**天然互补**，只是过去没往"业务数据"方向接。

### 1.3 第三个发现：公式引擎只在前端（这条容易被误判）

`web/src/engine/formula.testable.ts` 有 **30 个函数**（SUM/AVERAGE/IF/TODAY/NOW/ROUND/...），实现得挺完整。

但它**纯前端**。后端没有任何公式求值能力。

**这本来是坏事，但对我们其实是好事**——因为它逼我们做正确的设计：

> 🎯 **架构结论二：不要在服务端复用前端公式引擎。**
>
> 交期提醒需要判断的全部逻辑，就是 **`due_date` 和一个日期做减法**。
> 服务端只需要 `SELECT ... WHERE due_date <= ?`，**零公式求值**。
>
> 如果试图把公式引擎搬到 Go，那是巨大的浪费——而且会把"提醒"和"用户自定义公式"这两件事耦合在一起，后患无穷。

**推论**：`剩余天数` 应该是**展示时算出来的**，不是存储字段。库里只存 `due_date`。这样：
- 服务端查询极简（日期比较）
- 不会出现"存储的剩余天数过期了"这种脏数据
- 前端仍可自由用公式做更复杂的展示计算

## 三、第四个发现：加密边界不能被捅穿

Sheet 内容是加密的（`crypto.EncryptDocument`，master key 在 `MISTDOCS_MASTER_FILE`）。

但**已经有了明文元数据的先例**：`md_documents.title` 是明文列，只有内容加密。

**所以台账的设计要与这个先例一致**：

| 数据 | 存储 | 理由 |
|---|---|---|
| 订单号、客户、交期、状态、责任人 | **DB 明文列** | 需要索引/查询/告警；与 `title` 明文先例一致 |
| 工序工艺细节、图纸、备注长文 | **留在 sheet / 加密文件** | 敏感，且不需要被扫描 |

> 🎯 **架构结论三：交期 = 元数据（明文可查），工艺细节 = 内容（加密不可查）。**
> 不为了提醒功能去解密所有文档。

## 四、决策：建在哪、怎么切

三个方案，我列了取舍：

### 方案 A：全放 mist-docs
新增调度器（照抄 mist-team-server 的 ticker 模式，约 60 行）+ 台账表 + 提醒扫描。
- ✅ 单一服务，无跨服务耦合；交互/权限/通知全现成
- ✅ 交期提醒本质是文档域功能，语义上说得通
- ❌ 没有 AI；第二步（AI 提议层）要跨服务
- ❌ 调度器重复造

### 方案 B：全放 mist-team-server
- ✅ 调度/AI/规则/MCP 全现成，能力最强
- ❌ **没有表格 UI，要重写一套编辑器**——这是最大的浪费
- ❌ 它是"运维/命令审计"域，塞业务台账会污染领域边界

### 方案 C：按能力切（**推荐**）
- **mist-docs**：台账数据 + 交互界面 + 权限 + 站内通知
- **mist-team-server**：定时扫描 + AI 提议 + 外部推送 + MCP 暴露
- 连接方式：**已有先例**——`md_doc_fragments` 就是 mist-team-server 直接 JOIN mist-docs 的表（同库 `mist_team`）；且 `mistdocs.go` 已有跨服务 handler

> ### ✅ 架构结论四（决策）
> **方案 C。而且第一阶段不需要跨服务。**
>
> 第一阶段（交期看板）**完全落在 mist-docs 内**：新增一个轻量调度器就够——因为"到期扫描"是**纯日期比较 + 发通知**，不需要 AI、不需要规则引擎。
> 跨服务只在第二阶段（AI 提议层）才引入，那时调 mist-team-server 的 AI 能力，**复用已有的跨服务通道**，不新建基建。

**为什么不在第一阶段就跨服务？** 因为**过早分布式化是架构上最常见的错误**。一个 60 行的 ticker 不值得为此引入服务间调用、网络失败、版本协同、部署顺序这些复杂度。

## 五、数据模型设计

### 5.1 核心：台账（可查、可扫、可告警）

```sql
-- 订单/工单台账：交期看板的唯一数据源
CREATE TABLE md_deadlines (
  id            VARCHAR(32)  PRIMARY KEY,
  team_id       VARCHAR(32)  NOT NULL,
  department_id VARCHAR(32)  NOT NULL,

  order_no      VARCHAR(64)  NOT NULL,   -- 订单号
  title         VARCHAR(255) NOT NULL,   -- 产品/项目名
  customer      VARCHAR(128),            -- 客户（用于对外进度页时脱敏）
  quantity      INT,

  start_date    DATE,                    -- 计划开工
  due_date      DATE         NOT NULL,   -- ★ 交期，核心索引字段

  status        VARCHAR(16)  NOT NULL,   -- pending|running|done|overdue
  progress      TINYINT      DEFAULT 0,  -- 0-100
  priority      VARCHAR(16)  DEFAULT 'normal',  -- normal|urgent|inserted

  owner_id      VARCHAR(32),             -- 责任人（跟单员）★ 提醒发给谁
  remark        TEXT,

  created_by    VARCHAR(32),
  created_at    DATETIME,
  updated_by    VARCHAR(32),
  updated_at    DATETIME,

  INDEX idx_due    (team_id, due_date, status),  -- ★ 扫描主索引
  INDEX idx_owner  (team_id, owner_id),
  INDEX idx_status (team_id, status)
);
```

**关键设计点**：
- `due_date` 必须有索引，且和 `team_id` 组合 —— 扫描就是 `WHERE team_id=? AND due_date BETWEEN ? AND ?`
- `owner_id` 单独存 —— 提醒的收件人不需要再去查权限表
- `status` 独立列（不是算出来的）—— 「已延期」是**运维态**，不是"今天日期大过交期"这种推导值（否则无法区分"延期但已协商"）

### 5.2 提醒规则与幂等日志

```sql
-- 提醒规则：可配置，不必写死
CREATE TABLE md_reminder_rules (
  id          VARCHAR(32) PRIMARY KEY,
  team_id     VARCHAR(32) NOT NULL,
  name        VARCHAR(64),
  offset_days INT NOT NULL,      -- ★ T-N：提前几天（负数=逾期后）
  channel     VARCHAR(32),       -- inapp|webhook|wecom|email
  target      VARCHAR(32),       -- owner|manager|custom
  enabled     TINYINT DEFAULT 1,
  created_at  DATETIME
);

-- 提醒发放日志：★ 幂等的关键
CREATE TABLE md_reminder_log (
  id          VARCHAR(32) PRIMARY KEY,
  rule_id     VARCHAR(32) NOT NULL,
  deadline_id VARCHAR(32) NOT NULL,
  sent_at     DATETIME,
  channel     VARCHAR(32),
  result      VARCHAR(16),       -- ok|failed
  UNIQUE KEY uk_once (rule_id, deadline_id)   -- ★ 一天扫描 10 次也只发 1 次
);
```

> ⚠️ **幂等是这类功能最容易翻车的地方**。调度器每天跑或每小时跑，如果不去重，用户会被同一条提醒轰炸，然后**直接关掉通知**——功能就死了。
> `UNIQUE KEY (rule_id, deadline_id)` 是最简单可靠的方案。

### 5.3 变更留痕（AI 解释器的基础）

```sql
CREATE TABLE md_deadline_events (
  id          VARCHAR(32) PRIMARY KEY,
  deadline_id VARCHAR(32) NOT NULL,
  event_type  VARCHAR(32),    -- created|date_changed|status_changed|progress_updated|inserted_in
  field       VARCHAR(32),
  old_value   TEXT,
  new_value   TEXT,
  reason      TEXT,           -- ★ 为什么改（可选填，但这是最有价值的字段）
  actor_id    VARCHAR(32),
  created_at  DATETIME,
  INDEX idx_deadline (deadline_id, created_at)
);
```

**为什么现在就建这张表**：因为**历史数据无法追溯生成**。今天不记，三个月后想回答"这单为什么被推迟"就没有数据。而 `reason` 字段是未来 AI 交期解释器的燃料。

**这也是我们相对竞品的结构性优势**——小工单类产品大多只存当前状态，不存变更原因。

| 4 | CRUD + 视图查询 API | `internal/handler/deadline.go`（新） |

| 3 | "本月还能接几单" | 同底座 |

## 七、风险清单（按严重程度）

### 🔴 高：把台账做成"又一个表格"

**最可能失败的路径**：为了图快，直接把台账实现成"一张特殊 sheet"，然后又开始扫 blobs。
→ 这就是重复 Excel 的路。**必须在 DB 里。**

### 🔴 高：提醒轰炸导致用户关掉通知

调度器 + 无幂等 = 每天收 20 条一样的提醒 = 用户关闭通知 = 功能死亡。
→ `UNIQUE KEY (rule_id, deadline_id)`，**第一天就要有**。

### 🟡 中：调度器放错服务

放 mist-team-server 会强耦合；放 mist-docs 要新增基建。
→ 决策：**阶段一放 mist-docs**（自包含），阶段二再按能力切。**不要过早分布式化**。

### 🟡 中：`status` 用推导值

用"今天 > 交期"推导"已延期"，会导致**已协商延期**和**真延期**无法区分，且无法暂停提醒。
→ `status` 必须是独立可写列。

### 🟡 中：忽略变更留痕

不做 `md_deadline_events` → 三个月后无历史数据 → AI 解释器无燃料。
→ **现在建，成本极低，价值延后释放。**

### 🟢 低：加密边界

台账字段明文（与 `title` 明文先例一致），工艺细节留 sheet 加密。
→ 不需要改动加密机制。

## 八、一页纸架构总结

```
┌─────────────────────────────────────────────────────────┐
│  第一层：人的界面（mist-docs）                            │
│  DeadlineBoard.vue  ──  列表/看板/今日待交/负荷          │
│  SheetEditor.vue    ──  自由表格（产能表/班次表/测算）    │
└──────────────────┬──────────────────────────────────────┘
                   │  ①读写在同一个服务（阶段一）
                   │  ②跨服务调用已有通道（阶段二）
┌──────────────────▼──────────────────────────────────────┐
│  第二层：结构化台账（mist_team DB，可查可扫）              │
│  md_deadlines        ← due_date 索引，唯一数据源          │
│  md_reminder_rules   ← T-7/T-3/T-1/逾期，可配置          │
│  md_reminder_log     ← UNIQUE 键保证幂等                 │
│  md_deadline_events  ← 变更留痕（AI 解释器的燃料）        │
└──────────────────┬──────────────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────────────┐
│  第三层：引擎（阶段一在 mist-docs，阶段二切给 team-server）│
│  调度扫描  ── 复用 ticker 模式（~60行）                  │
│  推送通道  ── 复用 webhook + md_notifications            │

```

**四句话记住**：
1. **台账在数据库，不在文件里**（这是与 Excel 模板的本质区别）
2. **交期是明文元数据，工艺细节才是加密内容**（不捅穿加密边界）
3. **服务端只做日期比较，不搬公式引擎**（零公式求值）
4. **阶段一自包含，阶段二才跨服务**（不过早分布式化）

## 九、对前几份文档的两处修正

诚实标注，避免后面按错的理解去做：

1. **`02-整合稿` 说"交付形态是一张表 + 一个提醒"** → 表述欠明确，容易让人理解成"把 sheet 改造成台账"。
   **修正**：交付形态是**看板（实体+视图）**；表格只是其中一种视图形态，底层必须是 DB 台账。

2. **`03-AI融合` 说缺口是"ASR、轻量排产模型、历史统计"** → 这只说了 AI 侧。
   **修正**：还有第四个缺口，而且是**更前置的工程缺口**——**mist-docs 没有调度器**，以及**后端不解析业务数据**（因为只有 blob）。
   这两个不解决，AI 侧再强也无处落脚。
